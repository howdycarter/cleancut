### Vision: acceptance blocked

`VNGenerateForegroundInstanceMaskRequest` was actually performed against the
[480×640 synthetic bottle](synthetic-bottle.png). The framework returned:

```text
Error Domain=com.apple.Vision Code=9 "Could not create inference context"
UserInfo={NSLocalizedDescription=Could not create inference context}
```

See [raw error attachment](vision-error.txt). This identifies the observed
inference-context failure; it does not prove its underlying cause or that all
simulators lack the model. No real foreground mask was produced. Consequently,
subject retention, background transparency, and mask orientation are **not
accepted**. The opt-in test fails this gate when enabled and retains checks for
transparent background pixels, opaque subject pixels, PNG pixel equality,
dimensions, and rotated-mask agreement for a capable runtime/device.

### Photos: real PNG resource round trip

The test uses the production default `PhotoEditorViewModel.saveToPhotos()`
authorization and `PHAssetCreationRequest` writer. It then reads the newly
created asset's original resource through `PHAssetResourceManager` and checks
`public.png`, 64×48 dimensions, and equality of every decoded RGBA byte,
including transparent corners and the opaque red rectangle. No Photos writer
or PNG encoder is replaced. This proves the framework write/read path, not a
picker interaction, camera capture, or receiving share app.

Photos integration is restricted in code to a simulator and requires explicit
`CLEANCUT_PHOTOS_ACCEPTANCE=1` in the test process. The synthetic asset is retained
on the dedicated simulator for picker inspection. Physical-device libraries are
never enumerated by this test.

### Harness limitations encountered and corrected

- App-hosted unit tests cannot set `XCUIDevice.orientation` or use
  `XCUIScreen.screenshot()` on the iPad: XCTest reported “Not authorized for
  performing UI testing actions.” These APIs were removed. Device Hub's Controls
  → Rotate Left set the dedicated simulator to actual landscape; the host then
  checked the scene orientation and landscape window dimensions.
- A `UIScrollView` class assertion was removed: it was an invalid requirement
  when the iPad layout already fit the content. Reachability is reviewed through
  visible controls and real interaction, not an assumed SwiftUI backing class.
- The first ordinary iPhone run completed its tests but remained in Xcode log
  finalization for over eight minutes. Only that run's `xcodebuild` was
  interrupted. It ended with IDEFoundation Code 12: “Could not write the 1_Test
  action log because the log hasn't finished recording after waiting 30
  seconds.” Its summary and attachments remained readable; the raw test log is
  preserved. Later runs use `-collect-test-diagnostics never`.
- Runtime tests are opt-in for ordinary unit-test CI. The acceptance script
  enables real Vision and UI checks explicitly; a skipped gate does not clear
  release acceptance. Photos still requires the explicit synthetic-library flag.

## Follow-up: framework error classification and actual import UI

Apple's installed iPhoneSimulator 27.1 SDK `Vision.framework/Headers/VNError.h`
enumerates Code 9 as `VNErrorInternalError`. It is not an explicit missing-model
or unsupported-simulator error. Apple's [foreground request documentation](https://developer.apple.com/documentation/vision/vngenerateforegroundinstancemaskrequest)
and [WWDC subject-lifting session](https://developer.apple.com/videos/play/wwdc2023/10176/)
describe the request/handler/perform pattern used by the production service and
the independent test. These sources do not establish that this API always fails
on simulators. Do not call the observed error proof of a missing model.

On the dedicated iPhone runtime, a direct framework request fails before any
CleanCut mask application or export code. A second diagnostic request with
`usesCPUOnly = true` also failed with exactly the same Code 9 error; see
[raw diagnostic](vision-cpu-diagnostic.txt) and [result](followup-summary.json).
This narrows the observed failure to Vision inference in this runtime, outside
CleanCut's compositing path. Its underlying cause remains unidentified. No CPU
fallback was added to production, and no physical device result is assumed.

The real app was launched on the dedicated iPhone and inspected through Device
Hub. “Take a Photo” produced the expected camera-unavailable alert with a library
alternative; dismissing it recovered normally. The [actual picker](iphone-real-picker.png)
opened and a known generated red PNG was selected (no personal image was used).
The picker dismissed and the app showed its [processing-unavailable alert](iphone-import-unavailable.png),
consistent with the independent Vision failure; dismissing the alert returned
to the usable home screen. This verifies picker selection and failure recovery,
not successful real segmentation or camera capture.

The follow-up largest-type editor capture passed, but Device Hub accessibility
calls timed out twice during its bounded 60-second hold. Save reachability on
iPhone therefore remains an observed automation limitation and an unaccepted
check, not a proven application scrolling failure.

Essential device acceptance step: on an existing signed CleanCut installation
on a physical iPhone available to the user, use a licensed test photo with a
clear subject; verify foreground removal, transparent PNG corners/orientation,
then at largest text size scroll to and activate Save to Photos. No personal
photo, signing change, upload, or paid transaction is needed for this check.
